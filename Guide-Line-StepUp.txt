    J.6: Deploy to test, automatically

        Now Jenkins doesn't just build. It ships to passbook-test.

        The idea
        After the 3 build stages pass, a new stage:


        Frontend ✅ → Backend ✅ → Docker images ✅ → Deploy to test 🚀 → Smoke test 🔎
        Deploy to test: Jenkins uses the deploy-ssh key to SSH into passbook-test and run the same commands you typed by hand.

        One improvement over doing it by hand: instead of git pull (which takes whatever is newest on GitHub), the server checks out the exact commit Jenkins just tested (GIT_COMMIT). If someone pushes again during the build, test still gets exactly the version that passed.

        Smoke test: a quick check after the deploy: does the site answer? Does the API answer? If not, the build turns ❌ red, so you find out immediately.

        Your task
        Add these 2 stages after the Docker images stage, inside stages { }. Fill in the ???:


            stage('Deploy to test') {
            steps {
                sshagent(credentials: ['???']) {          // the credential ID you created in J.3
                sh """
                    ssh han@??? '                            # passbook-test's IP
                    cd ~/Personal-Site &&
                    git fetch --quiet origin &&
                    git checkout --quiet --detach ${env.GIT_COMMIT} &&
                    docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env.prod up -d --build
                    '
                """
                }
            }
            }

            stage('Smoke test') {
            steps {
                sh 'curl -fsS -o /dev/null http://???/'                    // the website answers?
                sh 'test "$(curl -s -o /dev/null -w "%{http_code}" http://???/api/me)" = 401'   // the API answers?
            }
            }
        Hints
        ???	Where to find it
        Credential ID	The ID you typed in Jenkins → Credentials (J.3 Step 5)
        IP (3 places)	passbook-test's IP, in your ~/.ssh/config under Host passbook-test
        New things explained
        Part	Meaning
        sshagent(credentials: [...]) { }	Loads the deploy key only inside these braces, and removes it afterwards. The key never appears in the log.
        sh """ ... """	Triple double quotes: a multi-line command where Groovy does fill in ${env.GIT_COMMIT} (with single quotes '...' it wouldn't)
        ssh han@IP '...'	Run everything between the single quotes on passbook-test
        git checkout --detach <commit>	Switch the server's code to that exact commit. "Detached" means not on a branch, which is normal for servers.
        &&	Run the next command only if the previous one succeeded, so a failed git fetch stops the deploy
        curl -fsS	-f = fail on an HTTP error (so the build turns red), -sS = quiet unless there's an error
        = 401	/api/me without a login should answer 401. That proves Caddy → Go API → works.
        Is .env.prod safe during git checkout? Yes. It's ignored by git, so checking out another commit never touches it. Each server keeps its own secrets ✅

    Kuma only tells you "up or down". For "how full is the disk, is RAM running out, which container eats CPU", each server needs small programs that publish its numbers. These are called exporters:

    Exporter	Reports	Port
    node_exporter	the whole VM: CPU, RAM, disk, network, uptime	9100
    cAdvisor	each container: CPU and RAM per container (api, db, web…)	8081
    Lesson 4's Prometheus (on ops) will fetch these numbers every 15 seconds. So the exporter ports must be reachable from passbook-ops only.

    3.1 Create deploy/docker-compose.monitoring.yml (PC, in the repo)

    # Metrics exporters for passbook-test and passbook-prod, scraped by Prometheus on passbook-ops.
    # Start on each server:  docker compose -f deploy/docker-compose.monitoring.yml up -d
    # network_mode: host = the ports belong to the VM itself, so ufw rules apply
    # (ports published the normal Docker way would skip ufw, see Lesson 1).
    name: monitoring

    services:
    node-exporter:
        image: quay.io/prometheus/node-exporter:v1.8.2
        restart: unless-stopped
        network_mode: host            # listens on :9100, sees the VM's real network cards
        pid: host                     # sees the VM's processes, not just its own
        command:
        - --path.rootfs=/host
        volumes:
        - /:/host:ro,rslave         # read-only view of the VM's disk, for disk usage

    cadvisor:
        image: gcr.io/cadvisor/cadvisor:v0.49.1
        restart: unless-stopped
        network_mode: host
        privileged: true              # needs to read container stats from the kernel
        devices:
        - /dev/kmsg
        command:
        - --port=8081               # default 8080 is a common port; keep it free
        - --docker_only=true        # only real containers, less noise
        - --housekeeping_interval=30s  # collect every 30 s instead of 1 s: much less CPU
        volumes:
        - /:/rootfs:ro
        - /var/run:/var/run:ro
        - /sys:/sys:ro
        - /var/lib/docker/:/var/lib/docker:ro
        - /dev/disk/:/dev/disk:ro
    Why network_mode: host this time? In Lesson 1 you learned that ports published with ports: skip ufw. With host networking there's no Docker port publishing: the exporter just listens on the VM, so your ufw rules protect it. That's exactly what we want here.
    Every mount is :ro (read-only), so the exporters can look but never change anything.
    Commit and push it. Jenkins doesn't start this file (it only runs the prod compose), so you start it by hand once. restart: unless-stopped keeps it running after reboots.

    Lesson 4: Prometheus on passbook-ops
    So far each exporter only shows the numbers right now. Prometheus visits all four exporters every 15 s, saves the numbers with timestamps, and lets you ask questions like "how much free disk did prod have yesterday?". In Lesson 5, Grafana draws graphs from it.


    passbook-test ─ node_exporter :9100 ─┐
                └ cAdvisor     :8081 ─┤        passbook-ops
    passbook-prod ─ node_exporter :9100 ─┼──►  Prometheus :9090  ──►  Grafana (Lesson 5)
                └ cAdvisor     :8081 ─┘   (pulls every 15 s, keeps 15 days)
    4.1 The config file: ops/prometheus/prometheus.yml (new file, PC)

    # Prometheus on passbook-ops: what to collect, and how often.
    global:
    scrape_interval: 15s        # visit every target every 15 s

    scrape_configs:
    # Prometheus checks itself
    - job_name: prometheus
        static_configs:
        - targets: ["localhost:9090"]

    # The VMs: CPU, RAM, disk, network
    - job_name: node
        static_configs:
        - targets: ["192.168.1.43:9100"]
            labels: { env: test, host: passbook-test }
        - targets: ["192.168.1.42:9100"]
            labels: { env: prod, host: passbook-prod }

    # The containers: api, db, web, ...
    - job_name: cadvisor
        scrape_interval: 30s      # cAdvisor only refreshes every 30 s (--housekeeping_interval), no point asking more often
        static_configs:
        - targets: ["192.168.1.43:8081"]
            labels: { env: test, host: passbook-test }
        - targets: ["192.168.1.42:8081"]
            labels: { env: prod, host: passbook-prod }
    A job is a group of targets of the same kind.
    Labels (env, host) get attached to every number from that target. Later you can write "prod only" as {env="prod"} instead of remembering IPs.
    4.2 Add Prometheus to ops/docker-compose.yml (PC)
    Add the new service under services: next to uptime-kuma, and the new volume at the bottom:


    prometheus:
        image: prom/prometheus:v3.15.0
        restart: unless-stopped
        command:
        - --config.file=/etc/prometheus/prometheus.yml
        - --storage.tsdb.path=/prometheus
        - --storage.tsdb.retention.time=15d    # keep 15 days of history
        - --storage.tsdb.retention.size=2GB    # ...or less, if it ever reaches 2 GB
        ports:
        - "9090:9090"                          # web UI: http://192.168.1.44:9090
        volumes:
        - ./prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro
        - prometheus:/prometheus               # the saved numbers survive restarts

    volumes:
    uptime-kuma:
    prometheus:
    ./prometheus/prometheus.yml is relative to the compose file, so it means ops/prometheus/prometheus.yml.
    Prometheus has no login. Anyone who can reach :9090 can read all your numbers. That's fine on your home network, but never publish 9090 on a server with a public IP.
    Guides often add --web.enable-lifecycle. I left it out on purpose: it lets anyone on the network shut Prometheus down with one HTTP request. You'll reload the config another way (4.6).

    4.6 Your first queries
    On http://192.168.1.44:9090, open the Query tab and try these. Switch to the Graph tab to see a line over time.

    Question	Query
    Is everything alive? (1 = yes)	up
    Free disk on /, in %	100 * node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}
    RAM in use, %	100 * (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)
    CPU busy, % (avg over 5 min)	100 * (1 - avg by (host) (rate(node_cpu_seconds_total{mode="idle"}[5m])))
    RAM per app container, MB	container_memory_usage_bytes{name=~"deploy-.*"} / 1e6
    Only prod's containers	container_memory_usage_bytes{env="prod", name=~"deploy-.*"} / 1e6
    node_cpu_seconds_total is a counter: it only ever goes up (total seconds of CPU since boot). rate(...[5m]) turns it into "seconds per second over the last 5 minutes", which is the CPU usage. Use rate() on any metric ending in _total.

    Changed the config later? Reload without losing data:


    docker compose -f ops/docker-compose.yml kill -s HUP prometheus
    HUP is the classic "re-read your config" signal; it's safer than the open HTTP endpoint.
